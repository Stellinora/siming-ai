# 本地建档超出 64K 上下文

## 实际故障

- 一部实际作品的章节建档失败，正文 5631 字符；本记录省略作品、章节名称及任务标识。
- 本地 `local_llama_cpp:qwen3.8-27b-q3` 返回 HTTP 400：`n_prompt_tokens=64523`、`n_ctx=64000`，错误类型 `exceed_context_size_error`。
- 最后一次执行在 2026-10-16 15:22:25 开始、15:54:13 暂停（北京时间）；此前有另一次执行和中间暂停，不能把任务总墙钟时间全部当作模型运行耗时。

## 根因

`run_cataloging_agent` 的固定工具循环持续追加请求消息，没有使用现有请求预算模块逐轮计量。保存候选工具返回完整恢复状态，旧状态在后续请求中重复保留。最终在提交确认前超过本地模型实际开放的窗口。

本次错误可由请求超限直接解释；服务仍运行，数据库为可写状态，候选仍保留。未通过增大模型窗口、删除正文或修改候选来绕过错误。

## 修复验收

- PC 固定建档循环每轮通过共享预算模块核算实际消息、当前工具格式、输出预留和安全余量。本地计量使用当前运行实例的模板和 tokenizer，显式 `chat_template_kwargs` 与实际生成请求一致。
- 触及预算时，使用完整数据库候选、当前校验结果、原章及已读档案原文、最近完整工具事务重新组装请求。仅替换重复历史状态，完整 `raw_output` 仍保留；首次整理后每轮刷新数据库检查点。
- 不通过代码猜测下一步工具，不自动 finalize，不截断原章或候选；完整必需资料仍超限时明确暂停。
- 真实安装续跑发现并补修冷启动顺序：只在实际建档执行中先通过既有 runtime manager 加载模型，再绑定 tokenizer 和实际窗口；只读预览不会启动模型。加载失败明确暂停，不发送生成请求。此前重启后模型未加载，字节上界将可容纳的候选错误地拦在调用之前。
- 后端 52 项建档回归（含冷启动）和 27 项共享本地计量/上下文回归通过；新增文件及计量文件 Ruff 通过。构建前架构、端间契约及打包后的 MCP 冒烟通过。
- Android 同步接入逐步预算和相同检查点边界；12 项 JVM 与 3 项 API 35 隔离模拟器测试通过，覆盖不连接 Gateway 的独立建档完成、保留候选后重试。手机使用现有保守 UTF-8 字节上界，因此整理时机可以与 PC 实际 tokenizer 不同。
