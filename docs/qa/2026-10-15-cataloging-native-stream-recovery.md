## 修复原则

- 携带原生工具的响应作为一个完整事务交付：说明文字和工具参数均在完成校验后交付。中断的响应不进入正式对话或工具执行。
- 传输中断时在有界次数内重新请求当前完整响应，保留原始消息及此前完成的工具事务；不拼接半份工具参数，不要求模型复述正文恢复标记。
- 思考片段仍可显示为活动进度，但接受的工具事务只保存最终成功响应的真实思考字段。
- 已完整返回但参数畸形的响应明确报协议错误；达到输出上限、拒绝和权限错误不会被当作网络中断无限重试。
- 无工具的正文生成继续使用已验证文字断点。两种恢复方式由实际工具契约确定，不解析用户文字来选择业务流程。

## 绕过应用的独立 HTTP 对照

随后诊断直接用 HTTP 客户端调用同一配置的硅基流动地址，仅请求模型生成，未执行任何返回工具，也未写入用户小说数据。两次调用均使用已配置模型和认证；请求上限 75 秒，无自动重试，无司命网关或 OpenAI SDK。

| 请求 | 结果 |
| --- | --- |
| 虚构角色的最小工具请求 | HTTP 200，4.83 秒正常收到 `tool_calls` 和 `[DONE]` |
| 原失败请求的完整消息、工具及参数 | HTTP 200，26.45 秒前收到 1033 字符工具参数，随后 40 秒未收到数据，66.45 秒读取超时；无完成原因或 `[DONE]` |

这证明该现象可在司命执行循环与 SDK 之外复现，且基本工具调用可用；仍不足以区分供应商内部生成、工具流转换与传输链路原因。请求包含 `enable_thinking=false`、`temperature=0.1`、`max_tokens=20000`，无自定义停止词或 JSON 输出模式。[官方接口文档](https://docs.siliconflow.cn/docs/api/chat-completions-post) 明确流式响应以 `[DONE]` 结束；[官方 V3.2 说明](https://www.siliconflow.com/zh/blog/deepseek-v3-2-now-on-siliconflow-reasoning-first-model-built-for-agents) 描述思考与非思考模式均支持工具调用。不能仅依据完整 JSON 绕过终止校验，也不能将最大输出额度误述为强制生成数量。
